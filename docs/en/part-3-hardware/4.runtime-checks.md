# 3.4 Runtime Checks and Safe Stop

## Purpose

This section lists checks before, during, and after hardware operation, plus abnormal-condition handling.

## Pre-Run Checks

| Item | Requirement |
| --- | --- |
| Environment | Flat, dry, open area with no unrelated people or fragile objects |
| Battery | Sufficient charge; no swelling, leakage, odor, or connector damage |
| Emergency stop | Hardware emergency stop, remote-control stop, or upper-computer stop command is available |
| Configuration | `config.yaml` matches robot model, SPI, IMU, and LCM channels |
| Model | New models and algorithms have been verified in simulation or on a safety stand |
| Processes | No old SDK, WebRTC, simulation, or external-algorithm process occupies control channels |

## Observe During Operation

- Whether the controller terminal continuously reports errors.
- Whether `log/robot_log.txt` records abnormalities.
- Whether state frequency in LCM monitoring is stable.
- Whether robot posture, gait, joint sound, and motor temperature are normal.
- Whether SDK, WebRTC, remote controller, and external algorithms send conflicting commands.

## Safe Stop

When ending normally or stopping, follow this order. Do not stop the controller with `Ctrl+C` first while the robot is still moving; directly killing the process may destabilize joints.

1. Send `DAMP` / `PASSIVE` / stop through the remote controller, SDK, or upper computer. Prefer `DAMP`; API numbers are in section 4.3.
2. If still uncontrolled, press the physical emergency stop.
3. After the robot is still, stop external-algorithm processes if any.
4. Finally press `Ctrl+C` in the controller foreground terminal.

## Abnormal Handling

If abnormal posture, leg twitching, control loss, continuous log errors, unusual sound, odor, or people approaching occurs, first perform safe-stop steps 1 to 3 above, then:

1. Shut off main power after confirming the robot has stopped.
2. Check battery, cables, connectors, SPI, IMU, and logs.
3. Do not run again before the cause is known.

## Prohibited Operations

- Run a new policy or external algorithm on hardware without simulation verification.
- Touch legs, joints, or the underside of the body while the robot is moving.
- Continue using an abnormal battery.
- Send conflicting commands from multiple control entries.
- Increase speed, torque, or PD parameters casually, or disable safety checks.
