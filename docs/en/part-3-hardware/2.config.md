# 3.2 Update config.yaml

## Purpose

This section explains the `config.yaml` items that must be checked and modified before hardware operation, especially Y15/E15 SPI configuration and IMU reading configuration.

## Prerequisites

- The current target is a real robot.
- MuJoCo simulation verification has completed.
- The on-site robot model, system architecture, SPI devices, and IMU type are known.

## Core Configuration

### Simulation Switch

```yaml
simulation:
  enable_mujoco: false
```

Hardware operation must disable MuJoCo. Simulation uses `config_sim.yaml` and LCM; hardware uses `config.yaml` and reads motor state from real SPI devices.

### Motor Communication

Example hardware configuration in the project root:

```yaml
motor_communication:
  type: "spi_legacy"
  spi_type: "E15"
  spi_device0: "/dev/spidev3.0"
  spi_device1: "/dev/spidev4.0"
```

`motor_communication.type` selects the motor communication implementation. `spi_type` can only be `E15` or `Y15` and is validated by `FSM_ConfigLoader`. It affects SPI rate, raw data structure, joint direction, and zero offsets. It is not the IMU type and does not automatically select an IMU driver.

#### SPI Device Number Configuration

Confirm actual device nodes on the target robot first:

```bash
ls -l /dev/spidev*
```

Then write the two existing nodes into `spi_device0` and `spi_device1`, and use controller startup logs to confirm the board0/board1 mapping.

#### Y15 and E15 SPI Difference

When switching to Y15, at minimum check:

```yaml
motor_communication:
  type: "spi_legacy"
  spi_type: "Y15"
  spi_device0: "/dev/site_confirmed_device0"
  spi_device1: "/dev/site_confirmed_device1"
```

### IMU

Y15 and E15 use different IMU vendors because the hardware platforms use different sensors: Y15 uses MicroStrain and E15 uses HipNuc. The software reads them through Lord and HipNuc drivers respectively.

IMU configuration is independent from Y15/E15 `spi_type`:

| Common combination | IMU config | Port example |
| --- | --- | --- |
| E15 + HipNuc | hipnuc | /dev/ttyS0 |
| Y15 + MicroStrain | lord | port_base=/dev/ttyUSB, port_number=0 |

Recommended fields:

```yaml
imu:
  type: "hipnuc"
  port_base: "/dev/ttyS0"
  port_number: 0
  baud_rate: 460800
```

Do not mix the three driver styles. HipNuc uses a full path; Lord usually uses a device prefix plus `port_number`.

Confirm actual ports from device enumeration:

```bash
ls -l /dev/ttyS* /dev/ttyUSB* /dev/ttyACM*
```

Do not set `port_base` to a full port and also configure `port_number` in a way that duplicates the path.

### LCM and Remote Control

```yaml
gamepad:
  device_type: "hybrid"
  lcm_control_channel: "QUAD_ROBOT_CONTROL"
  lcm_state_channel: "QUAD_ROBOT_STATE"
```

SDK, WebRTC, and controller must use the same LCM URL, control channel, and state channel.

### Safety Checks

```yaml
safety_checker:
  enable_safety_check: true
```

Do not disable safety checks on a real robot. Do not increase attitude, velocity, torque, or position limits without verification.

## Configuration Checklist

1. Confirm `simulation.enable_mujoco: false`.
2. Confirm `motor_communication.type` is the target SPI implementation.
3. Confirm `spi_type` matches the real communication board.
4. Use `ls -l /dev/spidev*` to confirm both SPI nodes exist.
5. Confirm IMU type, port, port number, and baud rate match the driver.
6. Start the controller and check SPI/IMU initialization logs.
7. Observe joint state, attitude, angular velocity, and safety-check state.
8. Stop first on any abnormality and return to configuration, device, and simulation checks.

## Success Criteria

- `config.yaml` is clearly a hardware configuration.
- SPI type and both device nodes match the site hardware.
- IMU type, port, and baud rate match the site hardware.
- SDK / WebRTC / external-algorithm channels match the controller.
- Controller logs show correct SPI type, device mapping, and IMU initialization.
- Joint angles, angular velocity, attitude, and IMU timestamps update continuously.
- Safety checks remain enabled.

## Troubleshooting

| Symptom | Common cause | Action |
| --- | --- | --- |
| SPI cannot open | Wrong device name or permission issue | Check `/dev/spidev*` and user permissions |
| Invalid `spi_type` | Typo or unsupported model name | Use only `E15` or `Y15` |
| SPI opens but joint direction is abnormal | SPI type, node order, offsets, or joint mapping are wrong | Stop and check `spi_type`, both nodes, and zero points |
| IMU cannot open | Wrong type, serial port, port number, or baud rate | Check `imu.type`, `port_base`, `port_number`, `baud_rate`, and `/dev/tty*` |
| IMU data does not change | Serial config issue, old driver, or disconnected sensor | Check IMU-loss logs from safety checks |
| Quaternion/attitude abnormal | IMU type or driver data order mismatch | Check driver type, startup logs, and attitude output |
| Duplicated port path | `port_base` is already a full path and a number is appended | Use full path for HipNuc; prefix plus number for Lord/AHRS |
| Robot shakes abnormally | Model, joint order, or PD parameters are wrong | Stop immediately and return to simulation verification |
