# 4.8 SDK Demo Usage

## Purpose

This section summarizes SDK demo usage order, environment variables, and common issues.

## Demo List

| Program | Source | Purpose |
| --- | --- | --- |
| `yobot_sport_client` | `example/sport_client.cpp` | Send motion-control commands |
| `yobot_robot_state_client` | `example/robot_state_client.cpp` | Read robot state |
| `yobot_http_server` | `example/http_server.cpp` | Start HTTP control service |

## Recommended Order

1. Start simulation or the hardware controller first.
2. Run `yobot_robot_state_client` and confirm state is readable.
3. Run `yobot_sport_client` and send small control commands.
4. Start `yobot_http_server` only when HTTP integration is needed.

## LCM URL

Same-machine operation usually works with the default LCM address. For multi-machine deployment, explicitly set:

```bash
export YOBOTICS_LCM_URL="udpm://239.255.76.67:7667?ttl=255"
```

Controller, SDK, WebRTC, and external algorithms must use the same setting.

## Troubleshooting

| Symptom | Action |
| --- | --- |
| No state after demo startup | Check controller, LCM URL, firewall, and multicast route |
| Control command has no response | Confirm that the robot mode accepts SDK control |
| HTTP token error | Check the `Authorization` request header |
| Cross-machine control is unstable | Use `monitor_lcm.sh --no-gui` to check channel frequency first |

## Safety Note

SDK demos are suitable for path verification. They are not recommended as unattended business programs. Add state confirmation, timeout protection, limits, and abnormal-stop logic for formal integration.
