# 5.5 wave_algorithm as the Joint-State Control Template

## Purpose

`wave_algorithm` is a rule-based joint-control template. It is useful for learning how to read development-mode state, generate 12-dimensional joint targets, and publish PD commands.

## Prerequisites

- The controller has entered `DEVELOPMENT` mode.
- LCM channel configuration is consistent.
- MuJoCo simulation has started.

## Design

`wave_algorithm` does not load an ONNX model. It generates actions from a sine wave:

1. Inherit from `AlgorithmBase`.
2. Override `_load_policy()` and skip policy loading.
3. Generate a periodic signal from time in `_run_inference()`.
4. Keep hip joints at default positions.
5. Offset thigh / calf joints by the sine wave.
6. Generate `joint_des_q`, `joint_des_qd`, `joint_des_tau`, `joint_des_kp`, and `joint_des_kd` in `process_action()`.

## Run

```bash
python3 external_algorithms/wave_algorithm/run_algorithm.py --config external_algorithms/wave_algorithm/config.yaml
```

Or enter the directory first:

```bash
cd external_algorithms/wave_algorithm
python3 run_algorithm.py --config config.yaml
```

## Success Criteria

- The program receives development-mode state after startup.
- LCM monitoring shows `Y15_development_command`.
- Robot joints move periodically as expected in simulation.
- No command remains after the algorithm exits.

## Configuration and Action Meaning

`wave_algorithm` uses `policy.type: none`, meaning no ONNX model is loaded. The base class still starts state receiving, inference loop, and LCM sending with the unified lifecycle, while `_load_policy()` sets `policy=None` directly.

Current configuration uses `motion.frequency` = 0.1 Hz and `motion.amplitude` = 0.5. Each leg is ordered as hip, thigh, calf. Hip keeps the default angle; thigh uses `amplitude * sin(phase)`; calf uses `-2 * amplitude * sin(phase)`.

`process_action()` finally generates these five 12-dimensional arrays:

| Field | Current behavior |
| --- | --- |
| `joint_des_q` | `default_joint_pos + action` |
| `joint_des_qd` | all 0 |
| `joint_des_tau` | all 0 |
| `joint_des_kp` | uses `joint_stiffness`, currently 60 |
| `joint_des_kd` | uses `joint_damping`, currently 2.0 |

Therefore `action` is a joint-position offset, not torque. Default angles are `[0.0, -0.8, 1.6]` repeated for four legs. Keep 12 dimensions and correct joint order when modifying them.

## Beginner Parameter-Tuning Flow

1. Keep `policy.type` as `none`.
2. Reduce `motion.amplitude` to 0.05 to 0.10 before first run; do not use 0.5 directly.
3. Keep `motion.frequency` at 0.1 and confirm motion direction in MuJoCo.
4. Change only one parameter before rerunning; avoid changing amplitude, frequency, and PD at the same time.
5. Use `monitor_lcm.sh --no-gui` to check whether the 12-dimensional targets in `Y15_development_command` are continuous.
6. Increase amplitude gradually only after simulation is stable.

## Troubleshooting

| Symptom | Possible cause | Check |
| --- | --- | --- |
| Joint direction is reversed | Default angle or joint direction is misunderstood | Give one joint a very small offset and observe joint by joint |
| Robot shakes | Amplitude, frequency, Kp, or Kd is too large | Reduce amplitude and Kp first |
| Hip also moves | Action index is wrong | Check the `leg_id * 3 + joint` index |
| No command | Not in DEVELOPMENT or no state | Monitor state and command channels together |

## Safety Note

Before hardware tests, reduce action amplitude and confirm every joint direction, default angle, Kp, Kd, and motion period. Rule algorithms have no model-level protection; wrong parameters are reflected directly in joint commands.
