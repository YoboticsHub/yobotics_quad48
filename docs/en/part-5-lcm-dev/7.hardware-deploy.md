# 5.7 Deploy Custom Algorithms on Hardware

## Purpose

This section explains the transition from simulation deployment to physical deployment for custom algorithms. The goal of hardware deployment is not to make the algorithm run immediately, but to confirm in an observable, stoppable, and reversible way that the simulation logic still holds on the real robot.

Default principle: simulate first, then use a stand or safety area; start with small amplitude and short tests. If anything is abnormal, return to `DAMP` or stop the controller, then go back to simulation debugging. Do not hide issues by increasing PD, torque, or limits.

## Prerequisites

- The algorithm has been verified in MuJoCo.
- `monitor_lcm.sh` can see development-mode state and commands.
- The algorithm publishes a disable command or safe command on exit.
- Hardware `config.yaml` has been checked for robot model, SPI, IMU, LCM, and safety checks.
- Emergency stop, stand, or safety area is ready.
- On-site personnel know how to switch back to DAMP or stop the controller.

## Simulation-to-Hardware Checklist

| Item | Requirement |
| --- | --- |
| Configuration consistency | Check `robot_id`, channel names, and model parameters |
| LCM channels | `Y15_development_state` and `Y15_development_command` are visible |
| SPI / IMU | Controller has no communication error and attitude data has no obvious jumps |
| Robot posture | roll/pitch are stable and below development-mode self-check threshold |
| Joint order | Matches the 12-dimensional order in `development_command_t` |
| Default joint angles | Match the physical initial posture |
| PD parameters | Do not exceed simulation-verified range |
| Action amplitude | Use small amplitude and short duration for the first run |
| Exit path | `Ctrl+C`, DAMP switching, and emergency stop are all confirmed available |

## Hardware Deployment Steps

1. Put the algorithm directory, configuration file, and model file into the robot-side software package.
2. Confirm that LCM URL, `robot_id`, state channel, and command channel in the algorithm configuration match `config.yaml`.
3. Send the package to the robot and start the hardware controller:

```bash
bash scripts/run_robot_controller.sh --config config.yaml
```

4. Read state and confirm stable robot posture.
5. Start LCM monitoring:

```bash
bash scripts/monitor_lcm.sh --no-gui
```

6. Enter `DEVELOPMENT` through SDK or another control entry.
7. First run `wave_algorithm` with reduced amplitude to confirm direction and exit logic.
8. Then run the custom algorithm, for example:

```bash
python3 external_algorithms/walk_algorithm/run_algorithm.py --config external_algorithms/walk_algorithm/config.yaml
```

9. Observe state through logs and LCM monitoring:

```bash
bash scripts/monitor_lcm.sh --no-gui
tail -f log/robot_log.txt
```

10. Keep the first run short. Exit actively after confirming state, commands, and posture are stable.

## Success Criteria

- Hardware controller has no SPI, IMU, LCM, or safety-check errors.
- External algorithm receives real robot state.
- Robot only performs small, stable, stoppable motions.
- Robot enters a safe state after the algorithm exits.

## Final Review Before Hardware

| Item | Requirement |
| --- | --- |
| Action amplitude | Use small amplitude and short duration first |
| Joint order | Exactly matches `development_command_t` |
| PD parameters | Do not exceed simulation-verified range |
| Frequency | Does not exceed what controller and LCM can handle stably |
| Safety checks | Keep enabled |
| Emergency stop | Can be triggered immediately on site |

## Monitoring Focus

| Item | Normal behavior |
| --- | --- |
| `Y15_development_state` | Updates continuously; `robot_id` is Y15 unless configured otherwise |
| `Y15_development_command` | Updates continuously during runtime and sends `enable_development_mode` = 0 on exit |
| Controller logs | No SPI, IMU, LCM, or safety-check errors |
| roll/pitch | Stable posture; self-check passes after external takeover exits |
| Joint targets | Continuous, no NaN/Inf, no obvious jumps |
| Actual joints | Follow targets without abnormal shaking, noise, or saturation |

`robot_id` must match controller configuration. Example configurations often use `"Y15"`; this is independent from the physical model.

## Abnormal Handling

| Abnormality | Action |
| --- | --- |
| Posture changes rapidly | Stop the algorithm immediately and switch to DAMP or emergency stop |
| Joint direction is wrong | Stop hardware testing and verify order joint by joint in simulation |
| Command loss or timeout | Check LCM frequency, network, and sending thread |
| Self-check fails | Check IMU, stand posture, and controller logs |
| NaN/Inf or dimension error | Stop deployment and debug model input |
| Shaking or unusual sound | Reduce amplitude and PD; return to simulation and do not continue hardware tuning |

## Safety Note

If physical motion differs from simulation, stop immediately and return to simulation debugging. Do not increase PD, torque, or speed limits to hide model, state-estimation, or joint-order problems.
