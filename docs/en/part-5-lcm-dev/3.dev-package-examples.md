# 5.3 Development Package Examples

## Purpose

This section introduces the `external_algorithms/` package structure and the two built-in examples. After reading it, users should understand how external algorithms read state, generate 12-dimensional joint commands, publish them to the controller through LCM, and decide which files to modify when creating a custom algorithm directory.

## Directory Structure

```text
external_algorithms/
├── README.md
├── algorithm_base.py
├── lcm_interface.py
├── walk_algorithm/
│   ├── config.yaml
│   ├── run_algorithm.py
│   └── quadTSnet.onnx
└── wave_algorithm/
    ├── README.md
    ├── config.yaml
    └── run_algorithm.py
```

## Core Files

| File | Purpose |
| --- | --- |
| `algorithm_base.py` | Configuration loading, policy loading, development-mode lifecycle, inference loop, LCM sending |
| `lcm_interface.py` | Subscribe to development-mode state and publish development-mode commands |
| `walk_algorithm/` | ONNX-based RL walking example |
| `wave_algorithm/` | Rule-based joint sine-wave control example |

## Overall Architecture

The external algorithm package has three layers:

| Layer | Main file | Purpose |
| --- | --- | --- |
| Communication layer | `lcm_interface.py` | Subscribe to controller state channel and publish development-mode command channel |
| Lifecycle layer | `algorithm_base.py` | Load configuration, warm up policy, run inference thread, run LCM sending thread, and send exit command |
| Algorithm layer | `run_algorithm.py` in each example | Generate actions from state and convert them into 12-dimensional PD commands |

On the controller side, `FSM_State_Development.cpp` broadcasts `development_state_t` and writes joint targets after receiving a legal `development_command_t`. External algorithms do not operate motors directly; they only publish development-mode commands.

## AlgorithmBase Responsibilities

`AlgorithmBase` is the common base for all external algorithms. Custom algorithms usually inherit from it and implement observation and action processing.

| Feature | Description |
| --- | --- |
| Configuration loading | Reads `config.yaml` under the algorithm directory |
| Policy loading | Loads ONNX when `policy.type: "onnx"`; rule algorithms can override `_load_policy()` |
| Policy warmup | When `warmup_count > 0`, runs inference with real state and checks action threshold |
| Inference thread | Calls observation, inference, and action processing at `execution.frequency` |
| Sending thread | Sends the latest command at `execution.lcm_send_frequency`, capped at 200 Hz |
| Auto start/end | Sends enable command automatically and sends `enable_development_mode: 0` on exit |

The two most important subclass methods are:

| Method | Purpose |
| --- | --- |
| `compute_observation(state)` | Converts `development_state_t` to an observation vector |
| `process_action(state, action)` | Converts action to five 12-dimensional arrays: position, velocity, torque, Kp, and Kd |

## LCMInterface Responsibilities

`LCMInterface` only wraps communication. It subscribes to `Y15_development_state`, decodes messages, filters by `robot_id`, constructs `development_command_t`, and publishes to `Y15_development_command`.

| Config item | Description |
| --- | --- |
| `lcm.url` | Empty string means the default URL |
| `lcm.state_channel` | Current example: `Y15_development_state` |
| `lcm.command_channel` | Current example: `Y15_development_command` |
| `lcm.robot_id` | Robot ID used to match state and commands |

## Run Examples

Walking policy:

```bash
python3 external_algorithms/walk_algorithm/run_algorithm.py --config external_algorithms/walk_algorithm/config.yaml
```

Wave control:

```bash
python3 external_algorithms/wave_algorithm/run_algorithm.py --config external_algorithms/wave_algorithm/config.yaml
```

Start MuJoCo or the hardware controller first and switch the controller to `DEVELOPMENT`. If only the Python script is started without controller state, it will not receive `development_state_t`.

## Create a Custom Algorithm Directory

Start by copying `wave_algorithm/` because it has no model dependency.

1. Copy the directory and rename it, for example `my_algorithm/`.
2. Update `algorithm_name` and LCM configuration in `config.yaml`.
3. Keep `policy.type: "none"` for rule algorithms; set model path for ONNX algorithms.
4. Implement `compute_observation()` and `process_action()` in `run_algorithm.py`.
5. Confirm observation order, action dimension, default angles, action scale, joint order, and PD parameters.
6. Run with small amplitude in simulation first, then inspect channels with `bash scripts/monitor_lcm.sh --no-gui`.

## Configuration Blocks

| Block | Purpose |
| --- | --- |
| `policy` | Policy type, model path, warmup, and abnormal-action threshold |
| `model_params` | Observation dimension, action dimension, default joint angles, Kp, Kd, action scale |
| `lcm` | LCM URL, state channel, command channel, robot ID |
| `execution` | Inference frequency, LCM sending frequency, auto start/end |
| `rl_mode` | Whether to process as reinforcement-learning mode |
| `debug` | Whether to print configuration and model metadata |

## Troubleshooting

| Symptom | Possible cause | Check |
| --- | --- | --- |
| Waiting for state forever | Controller not started, LCM network unavailable, channel name mismatch | Run `bash scripts/monitor_lcm.sh --no-gui` first |
| State exists but algorithm does not move | Not in `DEVELOPMENT` or `robot_id` mismatch | Check mode number `1005` and `robot_id: "Y15"` |
| ONNX loading fails | Wrong path or dependency error | Confirm model file exists and `onnxruntime` is installed |

The example default is often `"Y15"`, but this is only a matching string and does not mean the robot model must be Y15.

## Safety Note

Run external algorithms in MuJoCo first. Only consider hardware deployment after state receiving, command publishing, joint order, action amplitude, and exit logic are verified.
