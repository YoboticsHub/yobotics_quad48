# 3.2 修改 config

## 用途

本节说明实物运行前需要重点核对和修改的 config.yaml 项，重点解释 Y15/E15 的 SPI 配置和 IMU 读取配置。

## 前提

- 已确认当前运行目标是真实机器人。
- 已完成 MuJoCo 仿真验证。
- 已知道现场机器人型号、系统架构、SPI 设备和 IMU 类型。

## 核心配置

### 仿真开关

```yaml
simulation:
  enable_mujoco: false
```

实物运行必须关闭 MuJoCo。仿真使用 config_sim.yaml 和 LCM；实物使用 config.yaml，由真实 SPI 设备读取电机状态。

### 电机通信

当前项目根目录的实物配置示例：

```yaml
motor_communication:
  type: "spi_legacy"
  spi_type: "E15"
  spi_device0: "/dev/spidev3.0"
  spi_device1: "/dev/spidev4.0"
```

`motor_communication.type` 决定使用哪套电机通信实现：

`spi_type` 只能是 `E15` 或 `Y15`，由 `FSM_ConfigLoader` 校验。它影响 SPI 速率、原始数据结构、关节方向和零点偏置；它不是 IMU 类型，也不会自动选择 IMU 驱动。

#### SPI 设备号配置

在目标机器人上先确认实际设备号：

```bash
ls -l /dev/spidev*
```


再把实际存在的两个节点分别填入 `spi_device0` 和 `spi_device1`，并用控制器启动日志确认 board0、board1 的设备映射。

#### Y15 和 E15 的 SPI 差异


切换到 Y15 时，至少要确认：

```yaml
motor_communication:
  type: "spi_legacy"
  spi_type: "Y15"
  spi_device0: "/dev/现场确认的设备0"
  spi_device1: "/dev/现场确认的设备1"
```


### IMU

Y15 和 E15 使用不同 IMU 厂商，是因为实际硬件平台采用了不同的传感器：Y15 使用 MicroStrain，E15 使用 HipNuc。软件中分别由 Lord 和 HipNuc 驱动读取。

IMU 与 Y15/E15 的 `spi_type` 独立配置。下面的组合是当前项目的实际常见组合，但不是代码通过机型自动推导出来的：

| 常见组合示例 | IMU 配置 | 端口示例 |
| --- | --- | --- |
| E15 + HipNuc | hipnuc | /dev/ttyS0 |
| Y15 + MicroStrain | lord | port_base=/dev/ttyUSB、port_number=0 |

`spi_type` 只选择电机 SPI 协议和关节转换，`imu.type` 才选择 IMU 厂商驱动。更换机型时，应分别核对这两个字段，不能只修改其中一个。

代码实际根据 `imu.type` 选择驱动，推荐先按以下字段配置：

```yaml
imu:
  type: "hipnuc"
  port_base: "/dev/ttyS0"
  port_number: 0
  baud_rate: 460800
```


三种驱动的配置方式不能混用：HipNuc 使用完整路径；Lord 通常使用设备名前缀加 port_number。

实际端口以现场设备枚举为准：

```bash
ls -l /dev/ttyS* /dev/ttyUSB* /dev/ttyACM*
```


不要把 `port_base` 写成完整端口后又配置 `port_number` 进行重复拼接。

SPI 截图用于核对 `/dev/spidev*`，IMU 截图用于核对 `/dev/ttyS*`、`/dev/ttyUSB*` 或 `/dev/ttyACM*`。截图只能作为现场示例，最终仍以目标机器人实际枚举结果为准。

### LCM 和遥控器

```yaml
gamepad:
  device_type: "hybrid"
  lcm_control_channel: "QUAD_ROBOT_CONTROL"
  lcm_state_channel: "QUAD_ROBOT_STATE"
```

SDK、WebRTC 和控制器必须使用一致的 LCM URL、控制通道和状态通道。

### 安全检查

```yaml
safety_checker:
  enable_safety_check: true
```

真实机器人上不建议关闭安全检查，也不建议未经验证增大姿态、速度、扭矩和位置限制。

## 配置核对流程

1. 确认 simulation.enable_mujoco: false。
2. 确认 motor_communication.type 是目标 SPI 实现。
3. 确认 spi_type 与真实通信板匹配。
4. 用 ls -l /dev/spidev* 确认两个 SPI 设备节点存在。
5. 确认 IMU 类型、端口、端口编号和波特率与驱动匹配。
6. 启动控制器，检查 SPI/IMU 初始化日志。
7. 观察关节状态、姿态、角速度和安全检查状态。
8. 任何异常都先停止并回到配置、设备和仿真链路排查。

## 控制器启动后的确认

启动控制器后，优先检查日志中是否同时出现：

- 正确的 SPI 类型和两个 SPI 设备映射。
- 正确的 IMU 厂商驱动和串口设备。
- 关节状态持续更新。
- IMU 姿态、角速度和时间戳持续更新。


## 成功标志

- config.yaml 明确是实物配置。
- SPI 类型和两个设备节点与现场设备一致。
- IMU 类型、端口和波特率与现场设备一致。
- SDK / WebRTC / 外部算法通道与控制器一致。
- 控制器日志显示正确的 SPI 类型、设备映射和 IMU 初始化结果。
- 关节角、角速度、姿态和 IMU 时间戳持续更新。
- 安全检查保持开启。

## 常见问题

| 现象 | 常见原因 | 处理 |
| --- | --- | --- |
| SPI 打不开 | 设备名错误或权限异常 | 检查 /dev/spidev* 和用户权限 |
| spi_type 非法 | 拼写错误或使用了其他机型名称 | 只能使用 E15 或 Y15 |
| SPI 能打开但关节方向异常 | SPI 类型、节点顺序、偏置或关节映射错误 | 停止运行，核对 spi_type、两个设备节点和零点 |
| IMU 打不开 | 类型、串口、端口编号或波特率错误 | 检查 imu.type、port_base、port_number、baud_rate 和 /dev/tty* |
| IMU 数据无变化 | 串口配置错误、驱动未更新或传感器断开 | 查看安全检查中的 IMU 丢失日志 |
| 四元数/姿态异常 | IMU 类型或驱动数据顺序不匹配 | 核对驱动类型，检查启动日志和姿态输出 |
| 端口重复拼接 | port_base 已是完整路径又设置了编号 | HipNuc 使用完整路径，Lord/AHRS 使用前缀加编号 |
| 把机型和 IMU 强绑定 | 误以为 spi_type 会自动选择 IMU | 分别核对 spi_type 和 imu.type |
| SDK 无法控制 | LCM URL 或通道不一致 | 对齐 gamepad 和 SDK 配置 |
| 机器人异常抖动 | 模型、关节顺序或 PD 参数异常 | 立即停止，回到仿真验证 |
