# 5.6 以 walk_algorithm 讲 ONNX 模型仿真部署

## 用途

`walk_algorithm` 是基于 ONNX 策略模型的开发包示例，用于在开发者模式下验证用户自研或预训练的行走策略。

## 前提

- MuJoCo 仿真已启动。
- 控制器可以进入 `DEVELOPMENT` 模式。
- `external_algorithms/walk_algorithm/quadTSnet.onnx` 存在。
- Python 环境已安装 `onnxruntime`、`numpy`、`pyyaml` 和 LCM 绑定。

## 配置重点

| 配置项 | 说明 |
| --- | --- |
| `policy.type` | ONNX 示例使用 `"onnx"` |
| `policy.path` | ONNX 模型路径 |
| `model_params.num_obs` | 模型观测维度 |
| `model_params.num_actions` | 当前四足动作维度为 12 |
| `model_params.default_joint_pos` | 默认关节角 |
| `model_params.action_scale` | 动作缩放 |
| `execution.frequency` | 策略推理频率 |
| `execution.lcm_send_frequency` | LCM 命令发送频率，最高 200 Hz |

## 运行方式

```bash
python3 external_algorithms/walk_algorithm/run_algorithm.py --config external_algorithms/walk_algorithm/config.yaml
```

## 验证流程

1. 启动 MuJoCo 仿真。
2. 切换控制器到 `DEVELOPMENT`。
3. 运行 `walk_algorithm`。
4. 使用 `monitor_lcm.sh --no-gui` 检查开发模式状态和命令。
5. 观察 MuJoCo Viewer 中步态是否稳定。
6. 检查日志中是否有 NaN、Inf、维度不匹配或动作阈值异常。

## 成功标志

- ONNX 模型加载成功。
- 策略预热无异常。
- 观测维度和动作维度匹配。
- 机器人在仿真中能稳定响应策略输出。

## ONNX 加载与真实状态预热

AlgorithmBase 会根据 policy.type 为 onnx 创建 onnxruntime.InferenceSession。当前 read_metadata 为 false，因此 model_params 以 config.yaml 为准；如果打开 metadata，则还会尝试读取关节名、默认角、Kp、Kd、动作缩放和维度。

warmup_count 为 500 时，程序会等待真实 development_state_t，构造观测并推理 500 次，同时检查 action 是否超过 action_threshold。预热一直没有进度时，通常是没有收到 Y15_development_state，而不是模型本身没有加载。

## 45 维观测和历史观测

walk_algorithm 的 compute_observation() 当前使用 45 维：

| 区间 | 内容 |
| --- | --- |
| 0:3 | state.omega，机体角速度 |
| 3:6 | 由 state.quat 计算的重力投影 |
| 6:9 | [state.v_des[0], state.v_des[1], state.omega_des[2]] |
| 9:21 | state.joint_q - default_joint_pos |
| 21:33 | state.joint_qd |
| 33:45 | 上一帧 action buffer |

观测会裁剪到合理范围。基类还会维护历史观测队列，首次观测会填满历史，之后按从旧到新的顺序追加。当前 ONNX 推理假设模型恰好有两个输入：当前观测和展平后的历史观测。

## 动作处理和异常检查

动作处理公式为：

```
joint_positions = action * action_scale + default_joint_pos
joint_velocities = 0
joint_torques = 0
joint_kp = model_params.joint_stiffness
joint_kd = model_params.joint_damping
```

代码会检查 action 或目标中的 NaN/Inf、动作长度、缩放数组长度、默认角长度和最终 12 维长度。action 异常时会尝试使用上一帧 action buffer，仍异常则跳过本次命令。这些检查不能替代对观测顺序和训练配置的核对。

## 替换自己的模型

替换 ONNX 模型时必须同步检查：

| 项目 | 要求 |
| --- | --- |
| num_obs | 与训练时观测维度一致 |
| 历史输入 | 输入数量、历史长度和展平顺序一致 |
| num_actions | 输出维度为 12 |
| default_joint_pos | 与训练环境默认角一致 |
| action_scale | 与训练和仿真部署一致 |
| Kp/Kd | 不超过仿真验证范围 |
| 关节顺序 | 模型输出与 development_command_t 顺序一致 |
| 输入名 | 当前代码假设恰好有两个 ONNX 输入 |

如果模型只需要一个输入，或历史结构不同，应先修改 _run_inference() 并在仿真中验证。

## 常见问题

| 现象 | 可能原因 | 排查方法 |
| --- | --- | --- |
| Policy file not found | policy.path 错误 | 按配置文件所在目录确认模型路径 |
| 预热卡住 | 没有真实状态 | 监控 Y15_development_state |
| 模型输入报错 | 输入数量或维度不一致 | 检查 ONNX input 信息和历史长度 |
| action 超阈值 | 模型输出或观测构造异常 | 核对观测顺序、默认角和命令缩放 |
| 仿真动作发散 | 缩放、关节顺序或 PD 不匹配 | 降低 action_scale 和 PD，回到小幅验证 |

## 安全提示

替换 ONNX 模型后，必须同时核对观测构造、动作缩放、默认关节角、关节顺序、Kp、Kd 和输出裁剪。不要把只在脚本层能运行的模型直接部署到实物。
