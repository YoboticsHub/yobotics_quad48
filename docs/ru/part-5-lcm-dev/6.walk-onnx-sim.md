# 5.6 Развертывание walk_algorithm ONNX в симуляции

## Назначение

`walk_algorithm` — пример пакета разработки на основе ONNX-модели политики. Он используется для проверки пользовательских или предобученных политик ходьбы в режиме разработки.

## Предварительные условия

- Симуляция MuJoCo запущена.
- Контроллер может войти в режим `DEVELOPMENT`.
- `external_algorithms/walk_algorithm/quadTSnet.onnx` существует.
- В Python-окружении установлены `onnxruntime`, `numpy`, `pyyaml` и привязки LCM.

## Ключевая конфигурация

| Параметр конфигурации | Описание |
| --- | --- |
| `policy.type` | ONNX-пример использует `"onnx"` |
| `policy.path` | Путь ONNX-модели |
| `model_params.num_obs` | Размерность наблюдения модели |
| `model_params.num_actions` | Текущая размерность действия четвероногого робота — 12 |
| `model_params.default_joint_pos` | Углы суставов по умолчанию |
| `model_params.action_scale` | Масштабирование действий |
| `execution.frequency` | Частота инференса политики |
| `execution.lcm_send_frequency` | Частота отправки LCM-команд, ограничена 200 Hz |

## Запуск

```bash
python3 external_algorithms/walk_algorithm/run_algorithm.py --config external_algorithms/walk_algorithm/config.yaml
```

## Процесс проверки

1. Запустите симуляцию MuJoCo.
2. Переключите контроллер в `DEVELOPMENT`.
3. Запустите `walk_algorithm`.
4. Используйте `monitor_lcm.sh --no-gui`, чтобы проверить состояние и команды режима разработки.
5. Наблюдайте устойчивость походки в MuJoCo Viewer.
6. Проверьте журналы на NaN, Inf, несовпадение размерностей или ошибки порога действия.

## Критерии успешного выполнения

- ONNX-модель успешно загружается.
- Прогрев политики проходит без ошибок.
- Размерности наблюдения и действия совпадают.
- Робот в симуляции стабильно реагирует на выход политики.

## Загрузка ONNX и прогрев реального состояния

`AlgorithmBase` создает `onnxruntime.InferenceSession`, когда `policy.type` равен `onnx`. Сейчас `read_metadata` равно false, поэтому `model_params` берутся из `config.yaml`. Если чтение метаданных включено, код также пытается прочитать имена суставов, углы по умолчанию, Kp, Kd, масштаб действия и размерности.

Когда `warmup_count` равен 500, программа ждет реальный `development_state_t`, строит наблюдения, выполняет инференс 500 раз и проверяет, превышает ли действие `action_threshold`. Если прогрев не продвигается, обычно это означает, что `Y15_development_state` не получен, а не что сама модель не загрузилась.

## 45-мерное наблюдение и история

`walk_algorithm.compute_observation()` currently uses 45 dimensions:

| Диапазон | Содержание |
| --- | --- |
| 0:3 | `state.omega`, угловая скорость корпуса |
| 3:6 | Проекция гравитации, рассчитанная из `state.quat` |
| 6:9 | `[state.v_des[0], state.v_des[1], state.omega_des[2]]` |
| 9:21 | `state.joint_q - default_joint_pos` |
| 21:33 | `state.joint_qd` |
| 33:45 | Буфер предыдущего действия |

Наблюдения ограничиваются разумным диапазоном. Базовый класс также ведет очередь исторических наблюдений. Первое наблюдение заполняет историю, последующие добавляются от старых к новым. Текущий ONNX-инференс предполагает, что у модели ровно два входа: текущее наблюдение и выпрямленное историческое наблюдение.

## Обработка действий и проверки ошибок

Формула обработки действия:

```text
joint_positions = action * action_scale + default_joint_pos
joint_velocities = 0
joint_torques = 0
joint_kp = model_params.joint_stiffness
joint_kd = model_params.joint_damping
```

Код проверяет NaN/Inf в действиях или целях, длину действия, длину массива масштаба, длину углов по умолчанию и итоговую 12-мерную длину. Если действие аномально, код пытается использовать буфер предыдущего действия; если и он аномален, команда пропускается. Эти проверки не заменяют проверку порядка наблюдений и конфигурации обучения.

## Замена собственной моделью

При замене ONNX-модели проверяйте все перечисленное вместе:

| Пункт | Требование |
| --- | --- |
| `num_obs` | Совпадает с размерностью наблюдения при обучении |
| Исторический вход | Число входов, длина истории и порядок flatten совпадают |
| `num_actions` | Размерность выхода равна 12 |
| `default_joint_pos` | Совпадает с углами по умолчанию в обучающем окружении |
| `action_scale` | Совпадает с обучением и развертыванием в симуляции |
| Kp/Kd | Не превышает диапазон, проверенный в симуляции |
| Порядок суставов | Выход модели совпадает с порядком `development_command_t` |
| Имена входов | Текущий код предполагает ровно два входа ONNX |

Если модели нужен только один вход или другая структура истории, сначала измените `_run_inference()` и проверьте в симуляции.

## Устранение неполадок

| Симптом | Возможная причина | Проверка |
| --- | --- | --- |
| Файл политики не найден | Неверный `policy.path` | Проверьте путь модели относительно каталога конфигурационного файла |
| Прогрев завис | Нет реального состояния | Мониторьте `Y15_development_state` |
| Ошибка входа модели | Несовпадение числа входов или размерности | Проверьте информацию о входах ONNX и длину истории |
| Действие превышает порог | Аномален выход модели или построение наблюдения | Проверьте порядок наблюдений, углы по умолчанию и масштаб команд |
| Симуляция расходится | Несовпадает масштаб, порядок суставов или PD | Уменьшите `action_scale` и PD, вернитесь к проверке с малой амплитудой |

## Примечание по безопасности

После замены ONNX-модели проверяйте вместе построение наблюдений, масштаб действия, углы суставов по умолчанию, порядок суставов, Kp, Kd и clipping выхода. Не развертывайте модель на физическом роботе только потому, что она запускается на уровне скрипта.
