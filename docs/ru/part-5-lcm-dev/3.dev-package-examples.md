# 5.3 Примеры пакетов разработки

## Назначение

Этот раздел знакомит со структурой пакета `external_algorithms/` и двумя встроенными примерами. После чтения пользователь должен понимать, как внешние алгоритмы читают состояние, генерируют 12-мерные команды суставов, публикуют их в контроллер через LCM и какие файлы менять при создании каталога собственного алгоритма.

## Структура каталогов

```text
external_algorithms/
├── README.md
├── algorithm_base.py
├── lcm_interface.py
├── walk_algorithm/
│   ├── config.yaml
│   ├── run_algorithm.py
│   └── quadTSnet.onnx
└── wave_algorithm/
    ├── README.md
    ├── config.yaml
    └── run_algorithm.py
```

## Основные файлы

| Файл | Назначение |
| --- | --- |
| `algorithm_base.py` | Загрузка конфигурации, загрузка политики, жизненный цикл режима разработки, цикл инференса, отправка LCM |
| `lcm_interface.py` | Подписка на состояние режима разработки и публикация команд режима разработки |
| `walk_algorithm/` | Пример RL-ходьбы на основе ONNX |
| `wave_algorithm/` | Пример правилового синусоидального управления суставами |

## Общая архитектура

Пакет внешних алгоритмов имеет три слоя:

| Слой | Основной файл | Назначение |
| --- | --- | --- |
| Слой связи | `lcm_interface.py` | Подписка на канал состояния контроллера и публикация в канал команд режима разработки |
| Слой жизненного цикла | `algorithm_base.py` | Загрузка конфигурации, прогрев политики, запуск потока инференса, запуск потока отправки LCM и отправка команды выхода |
| Слой алгоритма | `run_algorithm.py` в каждом примере | Генерация действий из состояния и преобразование их в 12-мерные PD-команды |

На стороне контроллера `FSM_State_Development.cpp` рассылает `development_state_t` и записывает целевые значения суставов после получения корректного `development_command_t`. Внешние алгоритмы не управляют моторами напрямую; они только публикуют команды режима разработки.

## Ответственность AlgorithmBase

`AlgorithmBase` — общая база для всех внешних алгоритмов. Собственные алгоритмы обычно наследуются от него и реализуют обработку наблюдений и действий.

| Возможность | Описание |
| --- | --- |
| Загрузка конфигурации | Читает `config.yaml` из каталога алгоритма |
| Загрузка политики | Загружает ONNX при `policy.type: "onnx"`; правиловые алгоритмы могут переопределить `_load_policy()` |
| Прогрев политики | При `warmup_count > 0` выполняет инференс с реальным состоянием и проверяет порог действия |
| Поток инференса | Вызывает наблюдение, инференс и обработку действия с частотой `execution.frequency` |
| Поток отправки | Отправляет последнюю команду с частотой `execution.lcm_send_frequency`, ограниченной 200 Hz |
| Автостарт/автозавершение | Автоматически отправляет команду включения и при выходе отправляет `enable_development_mode: 0` |

Два наиболее важных метода подкласса:

| Метод | Назначение |
| --- | --- |
| `compute_observation(state)` | Преобразует `development_state_t` в вектор наблюдения |
| `process_action(state, action)` | Преобразует действие в пять 12-мерных массивов: положение, скорость, момент, Kp и Kd |

## Ответственность LCMInterface

`LCMInterface` только инкапсулирует связь. Он подписывается на `Y15_development_state`, декодирует сообщения, фильтрует по `robot_id`, создает `development_command_t` и публикует в `Y15_development_command`.

| Параметр конфигурации | Описание |
| --- | --- |
| `lcm.url` | Пустая строка означает URL по умолчанию |
| `lcm.state_channel` | Текущий пример: `Y15_development_state` |
| `lcm.command_channel` | Текущий пример: `Y15_development_command` |
| `lcm.robot_id` | ID робота, используемый для сопоставления состояния и команд |

## Примеры запуска

Политика ходьбы:

```bash
python3 external_algorithms/walk_algorithm/run_algorithm.py --config external_algorithms/walk_algorithm/config.yaml
```

Волновое управление:

```bash
python3 external_algorithms/wave_algorithm/run_algorithm.py --config external_algorithms/wave_algorithm/config.yaml
```

Сначала запустите MuJoCo или аппаратный контроллер и переключите контроллер в `DEVELOPMENT`. Если запущен только Python-скрипт без состояния контроллера, он не получит `development_state_t`.

## Создание каталога собственного алгоритма

Начните с копирования `wave_algorithm/`, потому что у него нет зависимости от модели.

1. Скопируйте каталог и переименуйте его, например в `my_algorithm/`.
2. Обновите `algorithm_name` и конфигурацию LCM в `config.yaml`.
3. Для правиловых алгоритмов оставьте `policy.type: "none"`; для ONNX-алгоритмов задайте путь модели.
4. Реализуйте `compute_observation()` и `process_action()` в `run_algorithm.py`.
5. Подтвердите порядок наблюдений, размерность действий, углы по умолчанию, масштаб действий, порядок суставов и PD-параметры.
6. Сначала запустите в симуляции с малой амплитудой, затем проверьте каналы через `bash scripts/monitor_lcm.sh --no-gui`.

## Блоки конфигурации

| Блок | Назначение |
| --- | --- |
| `policy` | Тип политики, путь модели, прогрев и порог аномального действия |
| `model_params` | Размерность наблюдения, размерность действия, углы суставов по умолчанию, Kp, Kd, масштаб действия |
| `lcm` | URL LCM, канал состояния, канал команд, ID робота |
| `execution` | Частота инференса, частота отправки LCM, автостарт/автозавершение |
| `rl_mode` | Обрабатывать ли как режим обучения с подкреплением |
| `debug` | Печатать ли конфигурацию и метаданные модели |

## Устранение неполадок

| Симптом | Возможная причина | Проверка |
| --- | --- | --- |
| Бесконечное ожидание состояния | Контроллер не запущен, сеть LCM недоступна, имя канала не совпадает | Сначала выполните `bash scripts/monitor_lcm.sh --no-gui` |
| Состояние есть, но алгоритм не двигает робота | Не включен `DEVELOPMENT` или не совпадает `robot_id` | Проверьте номер режима `1005` и `robot_id: "Y15"` |
| Загрузка ONNX не удалась | Неверный путь или ошибка зависимости | Убедитесь, что файл модели существует и `onnxruntime` установлен |

Значение по умолчанию в примерах часто `"Y15"`, но это только строка сопоставления и не означает, что модель робота обязана быть Y15.

## Примечание по безопасности

Сначала запускайте внешние алгоритмы в MuJoCo. Рассматривайте развертывание на физическом роботе только после проверки приема состояния, публикации команд, порядка суставов, амплитуды действий и логики выхода.
